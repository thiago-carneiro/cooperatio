# Artifacts of this production

The list and the graph of the artifacts this folder produces, with owner,
dependencies, schema and gates. The terms follow the [canon](01-canon.md); the
gates are defined in [`04-gates-and-rubric.md`](04-gates-and-rubric.md); the
owners are the roles in [`03-roles/`](03-roles/).

## Table

"Depends on" means: the artifact reads that input and becomes stale when it
changes. A note is not a dependency: a note from the validator or
from the review sends an artifact back to its owner without creating an edge
in the graph.

## The graph

Each arrow is "is read by". The graph is acyclic; the validator
checks this on every pass (gate `p-references`).

```text
corpus ──> brief ──> canon ──> artifacts ──┬──> cards
   │                  │                    └──> gates-and-rubric ──> instrument-validator ──> validator-tests
   │                  │                                 │
   └──────────────────┴──────────> recipe <─────────────┘
                                       │
                  ┌────────────────────┼────────────────────┐
                  v                    v                    v
            instance-car     instance-text-2027       instance-hpc
                  └────────────────────┼────────────────────┘
                                       v
                               validation-report
                                       │
                                       v
                    review (frozen rubric from gates-and-rubric)
                          │                 │
                          v                 v
                       replies          open-notes
                          └───────┬─────────┘
                                  v
                               lessons ──> readme

version ──┬──> changelog ──────────────┐
          ├──> registry ──> contracts  ├──> readme
          │               ^            │
          └──> round-record │            │
                           │            │
              canon ────────┘            │
              lessons ───────────────────┘
```

The second block is the versioning plane: `version` feeds the changelog, the
instance registry (whose shape the `contracts` schemas fix, together with the
note ledger), the round record and, through them, the readme. The license text
sits beside `version` as an owner record with no edges: nothing depends on it
and it depends on nothing. The experiments record (`experiments`, the
measurements about the method itself) reads the canon, the cards, the gates
and the registry, and feeds the readme; it is drawn in neither block, to
keep both legible. Neither is the declared semantics of the gates
(`gate-semantics`), which reads the gates and the canon and feeds no other
artifact, nor, since v0.5.0, the state ledger of the notes (`notes-status`,
which reads the open notes and the review and feeds the readme) and the two
documents of the adopter's surface, the root README and the skill
(`readme-root`, `skill`).

## What runs in parallel and what does not

- The three instances only start after the recipe passes its gates: it is
  the recipe that fixes what an instance has to fill in.
- The three instances are independent of each other; the same writer writes
  them in sequence, but none of them reads another.
- The review only starts after the validator passes on every
  document. Reviewing a text that the validator fails would spend
  the only review round on defects that the code already finds.

## Owner decisions as artifacts

The owner decisions listed in the brief do not get a file of their own here:
they are in the "Owner decisions" table of `00-brief.md`, and the open ones
appear in `90-review/notes.json` with target `corpus` or with the target of
the instance. The `version` artifact is the record of the one owner decision
this production writes into a file of its own.
